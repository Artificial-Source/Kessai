# How to build and release

This guide covers local builds and the repository release flow.

## Build locally

### Build frontend bundle

```bash
pnpm build
```

### Build desktop app bundle (Tauri)

```bash
pnpm tauri build -- --locked
```

(`pnpm build:tauri` is equivalent in `package.json`.)

### Build CLI/MCP binary

```bash
cargo build --locked --release -p kessai-mcp
```

Local one-shot checks after building:

```bash
./target/release/kessai-mcp --help
./target/release/kessai-mcp setup --dry-run
```

### Build web server binary

```bash
cargo build --locked --release -p kessai-web
```

## Run release quality gates

Install the headless browser and Rust audit prerequisites once. Chromium does not need a display; Linux may require administrator access for its system libraries. The Rust checks also need the [Tauri system dependencies](./install.md#build-from-source-developer-install).

```bash
pnpm exec playwright install --with-deps chromium
rustup component add rustfmt clippy
cargo install cargo-audit --locked --version 0.22.0
```

Before a release:

```bash
pnpm check
pnpm check:tauri-versions
pnpm test:run
cargo fmt --all --check
cargo clippy --locked --workspace --all-targets -- -D warnings
cargo audit
cargo test --locked --workspace
pnpm test:installer
pnpm audit --prod --audit-level=high
node scripts/release-dry-run.js --check
pnpm build
pnpm verify:web-resource
pnpm test:e2e:web-smoke
```

`pnpm check:tauri-versions` compares installed frontend Tauri packages with the exact Rust crate versions in `Cargo.lock` (major/minor) so lock refreshes do not break Tauri builds.

`pnpm release` runs the `before:init` gates listed in `.release-it.json`, including the production build and headless real-web smoke. The smoke runner creates an isolated temporary database and uses `KESSAI_API_PORT` (default `3001`); it never uses the normal app database. Reserve that port and install Chromium before starting a release. Set `CI=true` to enable CI-style Playwright retries and `forbidOnly`; a nonempty `CI=false` enables them too. Native desktop E2E is separate and is not implied by the web smoke gate.

## Create a release (maintainers)

Repository release process is automated via `release-it` + GitHub Actions.

Preconditions:

- Clean working tree
- On `main`
- CI passing

Dry run:

```bash
pnpm release:dry
```

`pnpm release:dry` first exercises version synchronization and artifact-validation regression cases, then requires a clean tree before invoking release-it. It restores `package.json`, the Tauri config, all user-facing Rust manifests, `Cargo.lock`, and `CHANGELOG.md` after the preview finishes, so the repo does not stay dirty or version-skewed from a dry-run. Do not run a release preview while another process is editing release-managed files.

For read-only preflight on a dirty development tree, use `node scripts/release-dry-run.js --check` (optionally followed by `vX.Y.Z`). This checks product versions and changelog agreement and runs synthetic tests, including rejection of every missing release asset. It does not run the full quality suites or change real manifests. `--self-test` runs only the synthetic regressions, including manifests whose dependency versions precede `[package]`.

### Releasing a version generated by release-it

Use this path when the new version and changelog have **not** already been committed:

```bash
pnpm release
```

After the local gates, release-it generates the version bump and changelog, synchronizes `package.json`, the Tauri config, the desktop, CLI/MCP, and web Rust package versions and their `Cargo.lock` entries, commits, tags, and pushes. The internal `kessai-core` crate retains its independent version.

### Releasing a pre-staged version (release branch)

Use this path when `release/1.0.0` already contains the committed `1.0.0` product versions, matching lockfile entries, and reviewed `CHANGELOG.md` section. Do not ask release-it to generate them again.

Fast-forward the release branch into a clean, up-to-date `main`, then release the version already on HEAD:

```bash
git switch main
git pull --ff-only
git merge --ff-only release/1.0.0
pnpm release -- --no-increment --no-plugins
```

If the fast-forward is not possible, resolve the branch history before releasing; do not substitute a merge commit. Keep the working tree clean and require passing CI for the release commit.

`--no-increment` preserves `1.0.0`; `--no-plugins` disables the external conventional-changelog plugin, so it does not prepend another generated changelog section. The configured lifecycle hooks still run: all `before:init` quality gates remain required, and `after:bump` still invokes the idempotent version-sync helper. With all versions already synchronized and committed, release-it tags `v1.0.0` on the existing HEAD and pushes the branch and tag.

Do **not** use `--no-increment` alone for this branch: it still loads the changelog plugin and prepends a second generated `1.0.0` section.

### GitHub artifact verification and publication

Either path pushes a stable tag that starts `.github/workflows/release.yml`:

1. Resolve the existing tag to one commit and verify agreement between the tag, `package.json`, Tauri config, user-facing Cargo manifests, `Cargo.lock` entries, and changelog.
2. Run the reusable CI workflow's quality, headless web-smoke, and Rust gates against that exact commit.
3. Create a draft release; all four desktop builds and all four CLI/MCP builds upload only to that draft, using locked Cargo dependencies.
4. In the final dependent publication job, download all assets, add desktop SHA-256 sidecars, and validate the exact inventory, every checksum, updater version/platform URLs, and matching signature sidecars.
5. Only after that verification succeeds, publish the release and make it latest. A failed check or missing artifact leaves the release unpublished.

Manual dispatch requires an explicit **existing** stable `vX.Y.Z` tag. It cannot release a branch. A rerun can resume a draft, but refuses to modify an already-public release. Builds check out the resolved commit, not the workflow's dispatch branch; publication also rejects a tag that moved during the build.

The exact required desktop inventory in `scripts/release-dry-run.js` is below (`<version>` is `1.0.0` for this release):

| Platform    | Required assets                                                                                  |
| ----------- | ------------------------------------------------------------------------------------------------ |
| Linux x64   | `Kessai_<version>_amd64.AppImage`, `Kessai_<version>_amd64.deb`, `Kessai-<version>-1.x86_64.rpm` |
| Windows x64 | `Kessai_<version>_x64-setup.exe` (NSIS), `Kessai_<version>_x64_en-US.msi`                        |
| macOS x64   | `Kessai_<version>_x64.dmg`, `Kessai_x64.app.tar.gz`                                              |
| macOS arm64 | `Kessai_<version>_aarch64.dmg`, `Kessai_aarch64.app.tar.gz`                                      |

Every desktop binary/archive requires an adjacent `.sha256`. The verifier requires `.sig` sidecars for the AppImage, NSIS `.exe`, `.msi`, both `.app.tar.gz` archives, **and the `.deb` and `.rpm`**; `.dmg` signatures are not in the inventory. Do not assume package formats produce updater signatures merely because they are installers: if a build does not produce the currently required `.deb`/`.rpm` sidecars, verification fails rather than treating them as optional.

`latest.json` must use the matching version and GitHub release-download URLs for `linux-x86_64` (AppImage), `windows-x86_64` (MSI), `darwin-x86_64`, and `darwin-aarch64` (the corresponding `.app.tar.gz`). Its signature strings must equal the adjacent nonempty `.sig` files. This release gate checks signature-sidecar agreement, not the signatures cryptographically against the updater public key. Missing, empty, or unexpected release assets block publication.

CLI/MCP release artifacts are also required for all four targets:

- `kessai-mcp-<version>-x86_64-unknown-linux-gnu.tar.gz`
- `kessai-mcp-<version>-x86_64-pc-windows-msvc.zip`
- `kessai-mcp-<version>-x86_64-apple-darwin.tar.gz`
- `kessai-mcp-<version>-aarch64-apple-darwin.tar.gz`
- adjacent `.sha256` for each archive (used by `install-cli.sh` / `install-cli.ps1`)
- archive contents include the binary, `LICENSE`, a `README.md`, and an offline copy of `skills/kessai`

Desktop release signing covers the Tauri updater channel. Apple Developer ID code signing and notarization are not part of the current workflow; macOS `.dmg` installs may need a Gatekeeper manual-open workaround until that is added. See [Install: macOS Gatekeeper](./install.md#macos-gatekeeper).

Release checksum sidecars detect corruption; they are not an independent authenticity mechanism. First-install trust remains GitHub HTTPS and the publisher. The existing Tauri updater signing key and endpoint are unchanged. Third-party workflow actions are pinned to commit SHAs with version comments; update pins deliberately when upgrading actions.

### Rehearse the workflow only in a fork

The new draft → artifact-verification → publication job sequence has **not been rehearsed end to end**. Passing local gates, `pnpm release:dry`, and synthetic artifact checks do not establish that the full GitHub workflow has reached the final `publish` job's artifact-verification step and published successfully.

Rehearse only in a fork with Actions enabled and the updater-signing secrets configured there. Use an existing stable tag matching the committed product versions and changelog (for this branch, `v1.0.0`), then inspect the resulting inventory, updater manifest, and final publication. The workflow and preflight script both enforce the stable-only regex `^v[0-9]+\.[0-9]+\.[0-9]+$`: a rehearsal tag such as `v1.0.0-rc.1` is rejected before builds. A successful fork run publishes a stable/latest release in that fork; do not use the upstream repository for rehearsal tags or releases.

## Important constraints

- Do not manually create release tags or GitHub Releases for normal flow.
- Use Conventional Commit messages for generated changelogs; preserve the reviewed section for a pre-staged release.
- Keep history linear on `main`; CI runs on pull requests, `main`, and `release/**` pushes.
- Run `pnpm release` from a clean `main` only.
